# أسلوب العمل Agile

نستخدم تكرارات قصيرة تنتهي بزيادة تعمل ويمكن فحصها. الفترة 3–8 أكتوبر مضغوطة؛ الـSprints أدناه تكرارات تسليم قصيرة وليست ادعاء تطبيق Scrum كامل أو توزيع عمل تم بالفعل.

## الدورة اليومية

- بداية العمل: 10 دقائق لمراجعة المنجز الفعلي، هدف اليوم، العوائق، وصاحب كل بطاقة.
- حد العمل الجاري: بطاقة تنفيذ رئيسية واحدة لكل عضو. أصلح فشل التكامل قبل إضافة شاشة جديدة.
- نهاية التكرار: Demo من clone قابل للتشغيل، ثم مراجعة قبول، ثم ملاحظة تحسين قصيرة.
- نطاق 8 أكتوبر يثبت في 7 أكتوبر؛ الميزات غير المؤهلة تُوسم بوضوح وتُنقل، ولا يُخفى نقصها.

## حالات البطاقة

`READY` معاييرها واعتمادياتها واضحة؛ `IN_PROGRESS` لها مالك وفرع؛ `REVIEW` لها PR وأدلة؛ `DONE` اندمجت وحققت القبول؛ `BLOCKED` يحدد السبب وصاحب فك العائق. حالة `BASELINE` في السجل الحالي تعني تنفيذًا في المحاكاة فقط، وليست DONE لمتطلب المختبر الكامل.

## الفروع والـPR

```bash
git switch main
git pull --ff-only
git switch -c feat/WQ-012-short-description
```

استبدل رقم المثال بالبطاقة التي أخذتها. استخدم `fix/` للإصلاح و`docs/` للتوثيق. اعمل commits صغيرة: `feat(planner): handle bounded hypotheses`. أضف في PR المشكلة والسلوك النهائي وطريقة الاختبار وحدود الدليل، وحدّث vault. تجنب force push على main. الحماية الآلية للفرع لم تُفعّل بعد؛ هذه سياسة فريق موثقة.

## Definition of Ready

هدف واحد، نطاق، صاحب، اعتماديات، واجهة متفق عليها، اختبار قبول يمكن إعادة تنفيذه، وبيانات اصطناعية محددة.

## Definition of Done

الكود يعمل، اختبارات ذات معنى ناجحة، مراجعة عضو آخر، لا أسرار أو بيانات حقيقية، تحديث الحالة والتسليم والقرار عند تغيّر البنية، دليل قابل للتكرار، ودمج ناجح. الشاشة وحدها أو mock وحده لا يكملان مرحلة enforcement حقيقية. قبل الدمج شغّل Python tests وfrontend build؛ CI يسجل النتيجة عن نفس commit عند تفعيله. حاليًا تفعيل GitHub Actions ينتظر صلاحية workflow؛ سجّل نتائج التحقق المحلي ومراجعة العضو الثاني.
